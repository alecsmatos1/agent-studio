# Usage and context tracking

Chats show compact progress bars directly below the message input: **Context**, **5-hour**, and **Weekly**. Selecting Claude Fable, including a CLI default that resolves to Fable, adds **Fable weekly**; other models never show it. Each limit shows only when the account's reading reports it, whatever the provider ([Limits an account does not report](#limits-an-account-does-not-report)), and the remaining bars fill the row. On narrow windows a bar's heading wraps with its value and pace arrow kept together. Credits appear inside the expanded usage panel. The context bar shows the latest response's provider-reported context count against the model's window in compact tokens, such as **35.2K / 1M**, rather than a percentage; its fill still shows the share used. Without a known window it shows the count alone, such as **35.2K tokens**. Before a measurement, or when a reply supplies no usable request-level count, it says **Not measured yet**. Unknown bars use a striped track and omit a numeric progress value, preserving the distinction from a measured zero.

Click any usage control to open reset times, budgets, credits, and guidance in a panel above the input. The panel leaves the message box and Send button usable and stays below the chat toolbar when a long draft makes the composer taller, scrolling its own content instead; close it with Escape, its Close button, or the same control. Its title and Checked text align vertically with Close. There are no gauge or refresh buttons. The expansion shows a **Fable weekly** card under the same Fable-only condition as its bar. Hover the Agent picker for the selected provider's tool-access policy; the message field's hover retains its keyboard shortcuts.

The **Agent** picker draws the same **5-hour** and **Weekly** bars for every account it lists, so the account with room left can be chosen at a glance. Each has its value, pace arrow and even-use guide, and its hover gives the reset time and pace. The bars sit beside the account's name, or below it when the list is narrow, and **Weekly** keeps its column when an account reports no 5-hour limit, so the accounts line up; an account whose reading reports no limit shows no bars. While the picker is open it reads each listed account whose usage can be read, on this computer or another, including one whose sign-in check finishes meanwhile; the native reader keeps a reading for a minute, so reopening stays cheap. A first reading shows **Checking…**, a reading that can no longer be refreshed stays as last reported without pace, and an account that needs signing in shows **Sign-in needed** instead of bars. The values also describe each option to screen readers, and clicking the bars chooses the account.

Usage updates immediately from Claude `rate_limit_event` and Codex `account/rateLimits/updated` and `account/updated` notifications on the selected account's chat process. The process reader captures these notifications even while the chat is parked. Codex updates merge sparse quota and credit fields, retaining other buckets, reset-credit counts, and each window's measurement timestamp. Claude's optional utilization is a fraction converted to a percentage; an allowed/warning/rejected status alone never invents a numeric reading. Only the documented general Claude buckets replace the general account windows.

Read-only checks remain a fallback once a minute while chat or Connections is visible, on return to the app, and after replies. They cover logins with no running/parked CLI and values absent from live notifications. Pushes invalidate the matching native cache, and a read started before a newer push cannot overwrite it. Account changes clear old readings, invalidate pending notices/confirmation, and recheck the exact connection's sign-in. A reading renews an expired login first, so a failed reading of a Claude or Codex account on this computer rechecks its sign-in too: Claude answers a lapsed login without limits and reports it signed out from then on, and the account then shows Sign-in needed in the Agent picker and Connections. Context capacity remains specific to the selected model.

Live account updates carry a host epoch, connection ID and revision. They remain in session memory, outside conversations, exports, prompt replay and run activity. Desktop receives a native event; paired Viewers receive the host's updates on the existing relay heartbeat (normally within five seconds). The authenticated relay and receiving transport verify the execution host and provider, reject browser publishers and foreign-host updates, and ignore duplicate, older, expired and retired-host updates. Unchanged windows do not receive a new pace timestamp merely because another bucket changed. No extra model reply or independent permanent CLI watcher is launched.

The expanded usage panel and Connections also read Codex `account/workspaceMessages/read`. Active messages render as plain text; inspection never opens links or changes account settings. Unsupported CLI/account responses show an unavailable notice. Notice text is transient, clears on selection/workspace changes, and travels through the existing authenticated job route for a remote account. Pending notice reads do not block relay disconnect or switching; late results are discarded, while pending redemption still blocks switching.

When Codex reports earned reset credits and at least 90% usage in a core 5-hour or weekly window, **Use a reset credit** opens a confirmation naming the selected account. Only **Use one credit** sends `account/rateLimitResetCredit/consume`. Native validation rechecks core eligibility and credit availability in the same restricted selected-profile app-server process used for redemption. Model-specific buckets do not establish eligibility. Uncertain retries reuse the same UUID idempotency key within the app session; `reset` and `alreadyRedeemed` both trigger a fresh limits read, while `noCredit` and `nothingToReset` report no reset. The UI does not infer new percentages or decrement balances from the redemption result. A failed refresh does not undo a confirmed redemption. Reset attempts are separate from the monetary credit balance and do not email a workspace owner or buy credits.

Protocol coverage checked September 20, 2026: freshly generated installed Codex app-server types, installed Claude Code 2.1.277 event schema and utilization conversion, and [official Codex account methods](https://developers.openai.com/pt-BR/docs/app-server). `scripts/live-usage-native-smoke.mjs` uses the isolated `scripts/native-live-usage.tauri.json` identity and disposable chat folders. It verified actual Codex/Claude event delivery and successful Codex workspace-message reads without consuming any real reset credit. Redemption and parked-output handling use controlled child-process tests. Managed WSL and remote provider processes were not live-tested for this feature; host routing, relay isolation and Viewer authorization have automated coverage.

## Credits

Click any context or usage bar to see Claude and Codex **Credits** in the expanded panel, or see the same reading beside each account's limits in Connections. Credits have no separate control in the bottom usage strip. These readings use the existing read-only usage query and exact account/computer routing, including remote and WSL connections. They refresh with account usage, stay in session memory, and retain the last reading on query failure. Older hosts without credit support show **Not reported**. Codex account balances display exactly two decimal places, truncating further digits (for example, `4,322.4487` displays as `4,322.44`); the underlying reading retains its precision.

- **Codex:** account credit balance, unlimited/available/no-credit status when reported, and a separate count of available usage resets. Read `rateLimitsByLimitId.codex.credits`, with the legacy `rateLimits.credits` fallback only when the multi-bucket view is absent or empty. Never borrow another model bucket's balance. The CLI reports no dollar conversion or percentage denominator; the USD equivalent below is a separate estimate.
- **Claude:** whether extra usage is enabled, spending this month, monthly spending cap, reported utilization, and remaining room under that cap. Read `rate_limits.extra_usage` from `get_usage`. Monetary amounts use the reported `currency` and `decimal_places`; missing units leave money unknown. The prepaid balance is not exposed by the supported CLI interface, so none is shown. Remaining room under a spending cap is never labelled a prepaid balance. Disabled extra usage still retains reported spending and cap amounts. Missing caps are not assumed unlimited.

Codex also shows **Estimated value (US$0.04 per credit)**, the rate in its label and no further note, based on the purchase options supplied on September 14, 2026: US$100 for 2,500 credits, US$200 for 5,000, and US$1,000 for 25,000. Thus 4,322.4487 credits display an estimated US$172.90. Calculate from the full balance and round money to two decimals; positive sub-cent values show `<$0.01`. This is a displayed-pack-price equivalent, not a CLI-reported dollar balance, refund value, or billed chat cost. The discount badges do not establish the final checkout amount, so do not apply them again; checkout discounts and taxes may change the actual cost. Missing, invalid, and unlimited balances have no numerical dollar equivalent. The estimate follows stale balance readings and remains outside the bottom usage strip. Claude keeps its reported currency amounts without applying the Codex conversion.

Zero, unavailable, disabled, and unlimited states remain distinct. Automatic tracking does not buy credits, redeem resets, change spending controls, or infer spending from per-reply costs. Earned resets use the separate confirmation described above.

Schema checks: installed Codex 0.153.4 generated app-server types; Claude Code 2.1.267 live read-only usage response and official SDK 0.3.267 types. [Codex account protocol](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/src/protocol/v2/account.rs) describes credit snapshots; [Claude usage credits](https://support.claude.com/en/articles/12429409-manage-usage-credits-for-paid-claude-plans) explains the separate credit balance and spending cap.

Verified September 14, 2026: `npm run verify` (192 unit/HTTP tests, production build, 129 browser scenarios), Rust formatting and Clippy, and 126 Rust tests passed; four existing opt-in Rust integrations remain ignored. `npm run tauri dev -- --config scripts/native-credits.tauri.json --no-watch` and `scripts/credits-native-smoke.mjs` verified live Windows queries for both providers with an isolated app identifier/profile. Browser coverage checks credit values, failed-refresh retention, drafts, keyboard closing, and desktop/mobile layouts; images were visually reviewed. Evidence is in ignored `artifacts/credits/` and `artifacts/credits-*.png`. Credit-specific live WSL and paired-remote checks were not run; routing remains on the existing usage transport, covered by the full suite. No provider responses were generated or billing settings changed.

## Reply usage and cost

The expanded usage panel includes **This chat**: saved input/output token totals and provider-estimated spend. Claude sums each reply's own reported cost once, including available failed/stopped results; older Claude replies that saved the conversation's running total instead are excluded and marked incomplete. Codex sums only newly scoped reply token readings. Its optional billing estimate covers the native session, so successive credit estimates are replaced rather than added. Missing historical readings stay incomplete; neither provider's subscription percentages are converted to money or exact per-chat consumption.

Codex 0.153.4 was checked with two replies to the same persistent native session through separate app-server processes. The second process resumed native history but reset its token counters (its output total was smaller than the first reply's). The adapter records these as `scope: reply`, keeps only the latest notification within a reply, and excludes unscoped older counters from the chat sum. A long-lived single-process integration must not reuse this interpretation without checking its baseline.

After a successful Codex turn, the existing parent process optionally reads `account/usage/read` with its exact loaded thread ID. Matching `threadUsage.estimatedUsageCreditsMicros` and `estimatedUsageUsdMicros` become separate `sessionCredits` and `sessionCostUsd` fields. Safe nonnegative integer micros are divided by one million; missing values, account summaries, other threads and breakdown groups are never substituted. The read is bounded to five seconds and cannot fail an otherwise successful reply. Live checks returned `threadUsage: null` for this account, both for a saved thread and a loaded thread: numeric Codex credit estimates are supported but not live-verified for this account. Controlled native protocol tests cover numeric estimates.

Each new Claude/Codex run also records revisioned **Account changes during this reply**, available in the usage panel for the latest reply and in each reply's timing expansion. Read-only queries take a fresh account snapshot before and after execution, through the exact profile/computer. Their elapsed overhead is excluded from completed reply timing. Cancellation can leave a missing final reading. Failed reads do not fail the reply or become zero. The optional message record retains only timestamps, labelled limit windows, credit balance/extra-use amounts, and reported currency; it contains no credentials or native session identity and is retained through workspace v3 save/export/relay. Ordinary dashboard caches remain session-only.

Quota changes require matching reset timestamps and nondecreasing percentages, with the reset still in the future. Display changes in percentage points. Credit-balance and extra-usage changes stay signed, preserving purchases and resets. All observations are explicitly **shared account** changes: other chats/devices, reporting delays, rounding, purchases and resets can contribute. They are not summed into attributed session charges.

Session tracking verification on September 14, 2026: 197 unit/HTTP tests, 131 browser scenarios, production build, Rust formatting/Clippy and 127 Rust tests passed (four preexisting opt-in Rust tests ignored). `scripts/session-spend-native-smoke.mjs` completed two real Windows replies per provider in an isolated QA app, verified fresh account observations, resumed-session token totals, saved Claude estimates and native reply durations, and captured the resulting UI. Numeric Codex session estimates are covered by the controlled native protocol test; this live account did not supply one. Desktop and 390 px mobile screenshots were inspected. Live WSL and paired-remote session-spend execution remain untested; existing routing and relay tests passed. Evidence stays in ignored `artifacts/credits/session-*` files. No billing settings were changed.

Each completed reply has a collapsed timing row below its final answer and artifact/progress cards, showing only the reply's elapsed time and cumulative total AI time. Work history is separately expandable below the model title. Expand the timing row with a click, Enter, or Space to see token counts, cached input, reasoning tokens when reported, elapsed time, and estimated cost in USD. Cached input is already included in input. Missing reply timing is labelled **Time not recorded**. Cost is stored with the reply and travels through relay checkpoints and saved history.

The same row also shows **total AI time** through that reply: the sum of its duration and all earlier saved assistant reply durations in the conversation. It includes recorded stopped and failed replies across model changes, and excludes user messages, idle time between messages, running replies, and separate conversations. Tool and child-agent times are already within the reply duration and are not added again. Totals are derived from saved durations, so history and relay updates retain them without another stored counter. Missing historical timing is marked with **≥** and explained in the expansion; if all timing is missing, the total says **Not recorded**. Elapsed and total times under a minute show tenths of a second (`4.6s`); from one minute on they show minutes, hours when needed, and whole seconds (`28m 31s`, `1h 7m 32s`). Native workflow run and agent durations use the same format.

Claude supplies `total_cost_usd` in each result, including failed results when present, but it is a running total rather than the reply's cost: it continues across every turn and compaction of one CLI process. Until 2026-09-22 Agent Studio stored that running total as each reply's cost and added the replies together, so replies on a reused process and chat totals were overstated. Each parked process now remembers the latest total it reported, and a reply records only the change: its last result's total minus the process's total when the reply started. A fresh process starts at zero. The CLI restores an earlier total only when a resumed session's previous process exited cleanly, and Agent Studio terminates parked processes instead; the opt-in `installed_claude_reply_costs_follow_each_process_running_total` test checks this against the installed CLI. A session resumed after a clean exit elsewhere, such as in a terminal, would have its restored total counted once in the next reply. A lower total, such as a zeroed failure result, leaves that reply's cost unknown and never lowers the remembered total; a successful result replaces it. These readings are saved with `scope: "reply"`. Reasoning tokens likewise come from each turn's `usage.output_tokens_details.thinking_tokens`, summed over the reply, not from the cumulative `modelUsage`. Older replies keep their saved running totals, which the reply footer labels **Chat cost so far** and the chat total excludes. Model and child totals are never added again. Codex's optional native-session estimate is shown separately; Codex and Antigravity have no per-reply USD cost field in the current adapters. Older saved replies also remain unknown. A reported zero is displayed as $0.00; tiny positive costs retain precision. Actual billing depends on the account plan. See [Claude cost tracking](https://code.claude.com/docs/en/agent-sdk/cost-tracking) and [subscription cost interpretation](https://code.claude.com/docs/en/costs).

## Subscription limits

These are account readings, not estimates from the number of local messages. They include usage from other sessions and title generation. The dashboard cache stays in memory; run observations are saved as described above. A limit the reading leaves out, or names without a percentage, is not shown at all, never as 0% (below). Failed refreshes retain the last successful reading and mark it **Last reported**. Readings older than three minutes, or whose reset time passed, are also marked as old; the app does not assume a reset succeeded or fabricate fresh capacity.

The readers launch installed CLIs in hidden processes and let each CLI authenticate normally. They do not read credential files, scan account transcripts, redeem reset credits, enable overages, or purchase anything.

| Provider | Read interface | Interpretation |
| --- | --- | --- |
| Codex | App-server `account/rateLimits/read` | Prefer `rateLimitsByLimitId`; classify windows by `windowDurationMins`, not primary/secondary position. Preserve separate model buckets; Spark readings only apply to Spark. |
| Claude | Stream-JSON control `get_usage`, with `skip_behaviors: true` | 5-hour and 7-day `utilization` are percentages used. Fable comes from the server-labelled `model_scoped` array. Do not interpret undocumented internal bucket names. |
| Gemini | Antigravity `--print /usage --output-format json` | Use only the Gemini Models group. Convert `remaining_fraction` to percentage used. An account can omit its 5-hour window. |

Claude's structured usage interface is marked **experimental** by its SDK. The implementation was verified against installed Claude Code 2.1.263 and the official `@anthropic-ai/claude-agent-sdk` 0.3.263 types. Unavailable/changed responses produce an unavailable or last-reported state. Occasionally `rate_limits_available: true` arrives with `rate_limits: null`; this is a failed reading, not a zeroed account. Read-only queries take as long as the CLI needs and are cancelled when the app quits.

### Limits an account does not report

Requested 2026-11-03, after Claude dropped the 5-hour limit from some plans: "When a meter is not reported (5h-limit) or (weekly) you can hide it instead of keeping showing … Make it generic so it works for everything."

A reading decides which limits show (`visibleLimits` and `accountLimits` in `src/lib/usage.ts`). The bars below the composer and their panel, the Agent picker and Connections show the 5-hour, Weekly and, for a Fable model, Fable weekly limits, and Connections the model-scoped ones too, only as the account's reading reports them with a share used. A limit the reading leaves out, as Claude Code's `get_usage` leaves `five_hour` out or null for such plans (its schema declares every bucket nullable and optional) and Codex does for most accounts, or names without a percentage, is not shown, for every provider and window. The composer's remaining bars fill the row, **Weekly** keeps its column in the Agent picker, and an account whose reading reports no limit, such as an API key's, shows no bars and reads **No limits reported.** in Connections.

Before an account's first reading, its 5-hour and Weekly limits wait in their places as **Checking…** on striped tracks while the reading is under way or due. In the composer that includes the time the selected account's check on this computer has not answered yet, and the reading starts as soon as the check finds the account ready. Without a reading and none coming (an offline computer, an account to sign in to, a browser that is not paired), and after a first reading that failed, no limit shows; retrying a failed reading leaves none waiting, so the bars do not come and go each minute. A later reading keeps to the limits the last one reported while it runs.

Live updates name only the limits they concern (a Claude `rate_limit_event` names one), so a snapshot made of them alone, before any read-only reading or after an account change, is `partial`: while a reading is under way the limits it lacks still wait as **Checking…**, and once the account has a complete reading, `snapshotFor` adds that reading's other limits to the newer updates, each as old as the reading that reported it, so pace never takes an old share for a new one.

## Replies stopped at a usage limit

When the account reaches a usage limit during a reply, the provider refuses the reply's next request. Claude Code answers the refusal itself: a parent assistant message with `model: "<synthetic>"`, `error: "rate_limit"` and `is_api_error_message: true` whose text is its own line about the limit, such as **You've hit your session limit · resets 1:50pm (America/Sao_Paulo)**, then an error result carrying the same line. Codex fails the turn with `codexErrorInfo: "usageLimitExceeded"`, in its `error` notification and in `turn/completed`'s `turn.error`. `src-tauri/src/protocol/usage_limit.rs` turns either into a revisioned `usagelimit` run event holding the provider's line, whole on one line, and never into a progress comment or the answer; a Codex turn stopped this way also keeps its last commentary in Work history. Claude lines are recognized by the openings Claude Code gives limits it reached ("You've hit your", "You've reached your", "You're out of usage credits" and the like), with or without the error kind, and never its warnings or notices; other refusals of the rate-limit kind, such as a temporary 429, stay ordinary failures. Claude Code's own messages ran no request, so they never replace the reply's reported model or context reading. The reply fails with the provider's line as its error, which alerts and clients without the card show.

The reply keeps the line as optional `usageLimit` (`src/lib/usage-limits.ts`) through history, export and relay checkpoints, merged by revision and kept when a relay from before the field drops it; it is never replayed into prompts. Until the reply completes, a warning card with the line follows its content, in place of the error card, as soon as the limit is reported, even while the reply still waits for background work. The card shows the provider's own line, which names any reset or advice, centred beside its button, and below it when the chat goes on by itself (below). For the latest reply of an idle chat whose agent has another account on that computer, **Switch account** in the card opens the Agent picker with each account's 5-hour and weekly usage. The reply's Work history stays open, labelled **Limit reached**, with every progress comment in place rather than the last one standing in for an answer, and still folds when clicked. Replies saved before 2026-09-30 name no limit, but reported `<synthetic>` as their model and kept Claude Code's line as their last progress comment: they show the same open history and card, leave such comments out of Work history, name the model chosen for them, and read no context from that message.

The message shapes were checked in Claude Code 2.1.285 (its limit wording and stream-json writer in the installed binary, and the user's saved replies from 2026-09-30) and in the Codex 0.159.2 app-server bindings from `codex app-server generate-ts`. No account was driven to a real limit for this.

### Going on once the limit resets

A chat a usage limit stopped goes on by itself once the limit resets (requested 2026-10-22, `src/lib/auto-continue.ts`). The computer that runs the chat, the desktop app or a server host and never the Viewer, plans it as the reply stops and saves the plan with that reply as optional `autoContinue`: `at`, when it sends the chat's next message; `off`, that it no longer will; `changedAt`. A plan without either is still being made.

- **When.** A minute past the later of two resets: the one the provider's line names, and the one of a limit the account's usage reading shows used up, Claude's own refusal included. Claude Code always names the zone of its time ("resets 1:50pm (America/Sao_Paulo)" within a day, "resets Oct 7, 1pm (…)" further on, with the year when it is another one), which is read in that zone; a time of day is its next one, or one at most five minutes before the stop, which the provider had not counted yet. Codex writes "try again at 3:05 PM" or "Oct 25th, 2026 3:05 PM" on the clock of the computer running it, which is the one that reads it. When neither names a reset, as for a used-up credit balance or an organization's limit, nothing says when the chat could go on: the plan is turned off once a reading of the account since the stop shows no limit used up, or ten minutes after the stop without one.
- **What it shows.** The card says **Continues at 1:51 PM** (with the weekday for later days, the date beyond a week) and **Cancel**, on every device that shows the chat, and **Waiting to continue** once the time has come.
- **When the time comes.** That computer reads the account's usage again. A limit still used up moves the plan to its reset. Otherwise, once the account can answer (its CLI there and signed in, no reply running), the chat is sent **Continue where you left off.** through the ordinary reply path, with the chat's next-reply settings: a message of Agent Studio's own (`sentBy: 'limit'`) that reads **Continued after the usage limit reset** above the reply it starts, has no Rewind here, and goes to the model as the user's next message. It goes on in the CLI process the stopped reply left parked, while that process is still there and its launch still matches ([NATIVE-SESSIONS.md](NATIVE-SESSIONS.md#persistent-processes)). A chat in History goes back to Active. A reading that fails leaves the outcome to the provider.
- **Pacing.** Each time going on comes to nothing, its reply stopping at a limit again before doing anything, the next wait past the reset doubles (2, 4, 8, 16, then 32 minutes), so a provider still refusing just after its reset is not asked every minute. A reply that did any work starts the count again.
- **What ends it.** Cancel, any message sent in the chat (yours, a workflow's, or the one sent at the reset), Retry, and a rewind past the reply. Once off a plan stays off: merges keep a cancel over any later change of the time, so a cancel on the phone wins over the computer moving the plan, and a rewind back to the stopped reply leaves the chat waiting for you. Forks and conflict copies never carry a plan. A workflow's chats are left to the workflow, which waits for resets itself, and a `/compact` reply is not continued.

The plan survives restarts (chats moved to History at startup still go on) and sync: merges keep it when a relay or app from before it drops the field, which also strips `sentBy`, so an older device shows the message sent as one of yours. The computer that runs the chat checks its plans every 15 seconds.

## Balancing new chats between accounts

**Settings → New chats → Start on the least used account** is off unless you turn it on. It belongs to the device: the desktop app and each Viewer keep their own choice (`preferences.balanceAccounts`), and it is never synced.

While it is on, a new chat starts on the account of its agent, on its computer, that has used the least, instead of the account last chosen. The agent is still the one last chosen. This covers every new chat that names no account: **Ctrl+N**, each **+** in the sidebar, the chat the app opens when it starts, the one **Move to history** leaves in a folder, `/new`, and **Chat** on an agent in Connections. **Chat** on an account's row in Connections names that account, which then stays.

Accounts compare by what is left of their **5-hour** limit, or of their **Weekly** limit when they report no 5-hour one, as most Codex accounts do, shared between the replies already running on the account and the new chat (requested 2026-10-26). Replies running together go on using up the same limit, which no reading shows before they do: an account at 30% of its 5-hour limit with two replies running leaves a new chat a third of the 70% left there, so the chat goes to another account with more room of its own. The comparison reads the limits the bars below the composer show for the chat's model, so a Claude Fable chat also counts each account's **Fable weekly** limit as one that can be used up.

- Accounts with room come first, then accounts without a reading, then accounts with a limit used up: one of those limits at 100%, or Claude refusing replies over the account's 5-hour or weekly limit, until the reset it named. When every account has a limit used up, the chat starts on the one that can answer again first.
- A limit whose reset time passed since its reading counts as unused. The bars still mark such a reading as old; balancing only compares by it, and reads the accounts again anyway.
- Accounts within 5 percentage points of the most room are level, as a limit within 5 points of its guide is on track. Level accounts take turns: first the one with the fewest replies running, then the one with the lowest weekly usage (for a Claude Fable chat, the more used of **Weekly** and **Fable weekly**), then the one that answered longest ago, then the order of the Agent picker. So chats started together spread over the accounts instead of all starting on the same one.
- The weekly limit decides only between level accounts. From 2026-10-22 to 2026-10-26 it came first while an account had used less than 80% of its 5-hour limit, and an account whose week had just begun took every new chat: three ran there together from 31%, 60% and 68% of its 5-hour limit and used it up within the hour, while the other account had used 2% of its own.
- Only accounts that can answer take part: none that needs signing in, whose CLI is missing, or whose computer is offline, and none that you left out.
- Workflow steps and dynamic workflow agents that name no account choose the same way, counting the replies of the steps and agents started before them.

Under the option, Settings lists the accounts it chooses between, agent by agent as the Agent picker does: every account connected beside another account of its agent on some computer, with its color, and with its computers when two share a name. Unchecking an account leaves it out: balancing never starts a new chat on it, on any computer where it is connected, and no longer reads its usage for that. It stays in the Agent picker and answers any chat you choose it for. With one account of an agent left, new chats start there; with none left, they start with the account last chosen, as with the option off. The accounts left out are kept on the device with the option (`preferences.balanceExcluded`), also while it is off, and an account added later takes part until you leave it out.

A new chat chooses at once from the readings the app already has, reads the usage of each of those accounts again, and chooses again once all of them answered. The readings are the Agent picker's: the same read-only query, kept for a minute by the native reader, so chats opened one after another read the accounts once. When the app starts it has no readings yet, so the chat keeps the account last chosen until they arrive. After that the choice stays while no other account has more room by more than those 5 points, so it does not move with every reading, and returning to the window reads the accounts again.

An account never changes under what you wrote. Once the composer holds text or an image, the account shown is the one the chat is sent with, however the accounts' usage changes; emptied again, the chat follows balancing again. The only choice made over text is the first one of a chat that opens with it, as `/new` does with the rest of its line, and never while mentions chosen under an account are in the draft. The choice does not move while the Agent picker is open either.

Choosing any account in the Agent picker, the one shown included, is your choice for that chat and stays. It is still remembered as the account last chosen, for when the option is off; an account balancing chose is not. While balancing decides, the Agent control's hover begins **Account chosen by usage.** A draft saved in an earlier session keeps the account it had.

Balancing only decides where a new chat starts. Existing conversations, their queued messages, retries, forks and imported chats keep their accounts, and balancing never moves a chat to another account while it runs; only an account you choose in the Agent picker does, from the next message on. The comparison uses usage readings and the saved chats alone (`src/lib/account-balance.ts`): it starts no model reply, and it reads the accounts' usage when a new chat opens and when you return to the window, at most once a minute each.

## Quota pace and context guidance

Arrows use plain 16px icons at the app's standard stroke weight, with no borders or colored backgrounds.

The panel and Connections show only the 24-hour time for resets today, such as **20:12**, and include the weekday for later days, such as **Saturday, 20:12**. Both use the viewer's local language and time zone. The full reset date remains available on hover. Missing reset times and resets awaiting an updated reading remain explicit. Both views retain usage, a remaining hourly/daily budget, and limit-reached warnings, without percentage-reduction advice. Pace is represented by bare trend arrows: green downward **Below pace**, blue right **On track**, amber upward **Ahead of pace**, and red upward **Limit reached**. Unknown pace uses a gray dash. Hover descriptions and accessible names retain the full meanings; quota bars use matching colors. The next-request estimate and Details section are removed.

Quota indicators compare the percentage used with the percentage of the full window elapsed. The guide assumes even use over the entire window, including nights and weekends; it is a planning aid, not an extra provider limit. The inferred window starts at the reported reset time minus its duration. Both sides of the comparison use the quota reading's `checkedAt` timestamp, so an unchanged reading does not become more favorable merely because the clock advances.

| Indicator | Meaning | Suggested action |
| --- | --- | --- |
| Green ↘ Below pace | More than 5 percentage points below the even-use guide | Room to spare compared with evenly spread usage |
| Blue → On track | Within 5 percentage points of the guide | Stay near the guide |
| Amber ↗ Ahead of pace | More than 5 percentage points above the guide | Ease usage to last until reset |
| Red ↗ Limit reached | Reported usage is at least 100% | Wait for reset or use another provider |
| Gray − Pace unavailable | Missing, stale, failed, expired, or inconsistent reading | Refresh for a usable reading |

For example, 70% used halfway through a window is ahead of the 50% guide. With 2.5 hours left in a five-hour window, the remaining allowance is 12% of the full limit per hour. Daily allowance is used for longer remaining periods; five-hour windows and periods with less than a day remaining use hourly allowance. Fable's extra window is assessed independently and only displayed for Fable.

Quota bars overlay the current colored fill and a secondary neutral recommendation on one track, sharing the same left edge and 0–100% scale. An endpoint mark keeps the recommendation visible when current usage passes it. Both the compact row and expanded cards omit a separate recommendation label; hover and accessible text retain the comparison. The recommendation uses the even-use guide at the reading's timestamp; context has no timed recommendation. Failed, stale, expired, or missing readings retain any known usage while hiding the recommendation.

Context has no timed reset. Its separate status uses the measured percentage: **Room available** below 80%, **Watch context** from 80%, **Nearly full** from 90%, and **At capacity** from 100%. **Growing quickly** applies below 80% when recent growth projects reaching 80% within three similar exchanges. These are app guidance thresholds. The context chip shows only its label and measured tokens, without a Reported badge or arrow. Its hover gives the exact counts and percentage used, then status and advice; status also remains in its accessible name; expanding the panel retains actionable warnings and growth estimates.

Growth uses up to six consecutive compatible measured readings (five increments), requiring at least three readings. Provider, model, reasoning, instructions, resolved model, and reported capacity must stay compatible. Missing readings, settings changes, and a decrease in context stop the trend; it never bridges a reset/compaction or mixes cumulative billing with context. The average measured growth provides an explicitly approximate number of similar exchanges to 80%. Projections beyond 20 exchanges are omitted; zero growth does not produce an infinite promise. Token room and practical advice to focus messages or carry a summary to a new chat appear in the expanded context card.

Typing leaves the measured reading and its guidance unchanged. Unknown measured context stays unknown while typing; no next-request or draft estimate is displayed. Pace and growth calculations run locally on existing readings and saved messages; they make no additional provider requests.

## Chat context and recorded tokens

The main context meter uses `contextInput` from the latest compatible reply, divided by its reported context window when available. Claude's reading is the latest API request's input plus cache-read and cache-creation input, matching its documented status-line formula. Output and cached-token billing are not added again. Hovering the token count shows the full number. The response's window takes precedence over a newly refreshed model catalog, so a historical reading is not silently recalculated against a changed model capacity.

Typing a draft does not change the reported meter. A running reply reports each request's count as that request starts, so a long turn shows its context while it runs instead of only at its result, which can come hundreds of calls later. Claude's `message_start` stream event carries the request's input before its first block (a long thinking block can otherwise hold the reading back for minutes), and its assistant lines repeat it; a sub-agent's requests and Claude Code's own `<synthetic>` messages never count. The decoder sends one `usage` event per new count, keeping the counts and cost of the reply's latest result (none before its first) and dropping the window reported for another model, so a reply stopped or cut off by an app close before its result keeps its last measured context. Codex reports the same as `thread/tokenUsage/updated` during the turn. A pending reply retains the previous reading until fresh usage arrives; a completed reply missing a context measurement clears the reading instead of reviving an older one. Changing provider, model, reasoning, or instructions requires a compatible new reading. Persisted request counts can be displayed even when an older reply has no local prompt estimate. An explicit zero is a real reading; an absent count is unknown.

**Current adapter coverage:** Claude reports request-level context. Codex app-server reports the latest request's `last.inputTokens` and its model context window. Antigravity result totals are retained as token totals and are not relabelled as exact context.

Agent Studio starts a fresh CLI process for each reply, resuming the exact host-local native session for Claude and Codex. Legacy history is bootstrapped once. The UI displays only measured context; local prompt estimates remain internal metadata and are never substituted for a provider reading.

Capacity comes from a response's `modelUsage.contextWindow`, Codex's CLI-maintained `models_cache.json` effective window, Claude's read-only `get_context_usage` summary for the selected model, and the published Gemini input limit for the explicitly supported model families. A separate read-only summary supplies model capacity only; it is not the chat's live context session. Unknown models have unknown capacity; no universal model limit is guessed. Gemini's published limit can differ from a CLI's reserved/compaction budget. Native session resumption is handled by the provider adapters; this panel does not implement compaction.

Reported input, output, cached input, and available reasoning counts are saved on each reply. The usage panel sums verified reply readings as described above. Older replies without usable counts remain explicitly unmeasured. Title usage is included in account limits but not in per-chat totals. Workspace v3 accepts the additional optional fields without dropping existing conversations.
